# Backends: notes for agents

A backend implements `CompilationBackend` (`CompilationBackend.hpp`):
`compile(ir, dumpHandler, options, statistics)`, its exception-propagation
mode and the IR optimization level it needs. The engine's front end produces
NIR: a backend that returns true from `compilesNir()` reads the module the graph
carries (`tbc`, `cpp`, `asmjit`, `mlir`), the others get the 0.3 IR built from it first (`compiler/NirToIR.cpp`)
until their NIR port lands. Built-in backends are registered
in `CompilationBackend.cpp`; plugins call `CompilationBackendRegistry::registerBackend`.
A backend that reads what only the 0.3 trace carries returns true from `needs03Frontend()` (the GPU backends: the `kernel`
attribute of a function); the engine then uses the 0.3 pipeline when `engine.backend` pins it.

| Backend | Directory | Notes |
|---|---|---|
| `asmjit` | `asmjit/` | `X64LoweringProvider`, `A64LoweringProvider` over AsmJit's `Compiler`; register allocation is AsmJit's (`third_party/asmjit`, Nautilus patches marked `[Nautilus]`); post-RA peepholes. Check generated code with `dump.after_asmjit_assembly` |
| `tbc` | `tbc/` | threaded bytecode with tail-call dispatch; `tbc.mode=jit` uses copy-and-patch stencils (`tbc/jit`, regenerated by the `tbc-regen-stencils` target, Clang ≥ 19) |
| `mlir` | `mlir/` | NIR → MLIR → LLVM → ORC JIT (`MLIRNirLowering`); the 0.3 IR path (`MLIRLoweringProvider`) stays for `tracing.nirTracer=false` and for `debug`/`perf`. Needs the MLIR download (`full` preset) |
| `cpp` | `cpp/` | C++ source compiled by the system compiler into a shared library; slow (20-30 ms, nearly all of it the system compiler), for debugging |

- **Intrinsics:** plugins register native functions in `ir/IntrinsicRegistry`;
  a backend may replace the call with inline code (`asmjit/intrinsics/`,
  `mlir/intrinsics/`). The native function must stay a correct fallback.
- **Exceptions:** backends without unwind tables (`asmjit`, `tbc`) catch
  through capture thunks (`CapturedExceptionTransport`); MLIR code unwinds
  natively.
- **Every backend change** needs `nautilus-execution-tests` on that backend and
  the fuzzer replay; for `asmjit`, also diff the assembly dumps before and
  after (`perf-investigation` skill). Patches to `third_party/asmjit` must keep
  the `[Nautilus]` markers.

## NIR backends (0.4)

- `nir/NirBackend.hpp` is the 0.4 interface (`NirBackend::compile(shared_ptr<const nir::Module>, CompileContext)`) with
  a registry; it lives next to `CompilationBackend` until the cut-over. `tbc/TBCNirLowering.cpp` lowers SSA NIR into the
  same `TBCProgram` as the 0.3 lowering, so dispatch skins, stencils and the executable are shared.
- D10/D11 are lowered in bytecode, not in handlers, so the stencils do not change: a checked `div`/`rem` compares and
  branches to a cold block that calls `nautilus_rt_throw_arith` through its capture thunk, shift amounts are masked,
  `fptosi`/`fptoui` call the saturating helpers of `nir/NirRuntime.cpp`.
- `cpp/CPPNirLowering.cpp` prints C++ from SSA NIR (M4.3): values of integer and pointer types are unsigned integers of
  their width, so arithmetic wraps and the signed view is a cast; checked `div`/`rem` test the divisor (and the minimum
  divided by -1) and throw through the same captured-call `try` as calls that may throw; shift amounts are masked;
  `fptosi`/`fptoui` use saturating helpers emitted into the source; memory goes through `__builtin_memcpy`. Every function
  is an `extern "C"` symbol `nfn_<index>` with its exact name as an assembler label (quoted when it is not an identifier),
  since the engine looks functions up by name. The generated code points into the module (data objects, bindings), which
  the executable keeps alive.
- `tools/nir-run` (`nautilus-nir-run`) compiles a `.nir` file and runs its `; run @f(args) = result` directives;
  ctest runs `test/data/nir-run/*.nir` on `tbc` in three modes, on `cpp` and `asmjit` (native executables are called through dyncall) and on `mlir` (called through a typed function pointer so that exceptions unwind). Add a file there for every NIR operation a backend
  handles.
- `TBCBackend::compile` hands a graph that carries a NIR module and no IR to `TBCNirBackend`; the `tbc.registerAllocator`,
  `tbc.coalescing`, `tbc.superinstructions` and `tbc.immediates` options belong to the 0.3 lowering only.
- The execution tests run every backend on the default pipeline, plus `legacy-tbc` and `legacy-asmjit` (the 0.3
  pipeline, `tracing.nirTracer=false`) and the pseudo-backends `nir-tbc` and `nir-tbc-jit`: with the 0.3 tracer,
  `tracing.nirChain=true` converts the trace to SSA NIR (`toPreSSA` -> conversion) and attaches it to the IR graph, and
  the `nirtbc` backend compiles that NIR with `tbc` on NIR. They go with the 0.3 pipeline.
- `mlir/MLIRNirLowering.cpp` lowers SSA NIR to `func`/`cf`/`arith`/`llvm` (M4.5): block arguments are MLIR block
  arguments, `condbr` weights come from `prob`, a call whose unwind entry is a pad is an `llvm.invoke` to an
  `llvm.landingpad` block that branches to the pad body (which receives the exception as a block argument, so a pad can
  also be entered by `br` from another pad; `resume` is `llvm.resume`), and a call with `NO_CLEANUP` is a plain call that
  unwinds natively through the frame. D10/D11: a checked `div`/`rem` compares the divisor (and the minimum against -1) and
  branches to a cold block that calls `nautilus_rt_throw_arith` (an `invoke` when the entry is a pad), shift amounts are
  masked, `fptosi`/`fptoui` are `llvm.fptosi.sat`/`llvm.fptoui.sat`. A bool occupies a byte in memory. Native functions
  are declared as `func.func private` with the extension attributes of their signature and registered with the JIT by
  address; `engine.normalizeFunctionNames` names them `runtimeFunc<N>` (stable reference IR), the inlining plugin's
  `callNameOverride` hook still renames them by address.
- **Intrinsics on NIR:** a handler is `bool(NirIntrinsicCall&)` (builder, lowered operands, result type, `result`), registered
  with `MLIRIntrinsicManager::addIntrinsic`, which also adapts it to the 0.3 lowering. The NIR lowering looks a handler up by
  the address of the native function, for external callees as for intrinsic ones (the plugins register by address; only
  atomics and `assume` are in the `ExtensionRegistry`). A handler that reads the address of a traced pointer operand finds
  it in the `llvm.inttoptr` of an `arith.constant` (`simd` shuffle). `NirExtensionHooks` is the hook for the MLIR type and
  the lowering of an extension type and operation (M6.5); nothing is registered by the core.
- **State reuse (#561):** `MLIRThreadState` keeps the `MLIRContext` (no thread pool unless `mlir.enableMultithreading`) and
  the `TargetMachine` of each (CPU, level) per thread, and the host is detected once per process; a worker that promotes many
  functions pays them once (`mlir.contextsCreated`, `mlir.targetMachinesCreated` in the statistics). The ORC JIT uses the
  machine too: `ThreadTargetMachineCompiler` is the code generator LLJIT is given, and it looks the machine up in the
  state of the thread that generates the code, which need not be the one that created the JIT (ORC generates code at the
  first lookup), so it never stores it. The data layout comes from the same machine. LLJIT's own, one machine for the
  layout and one per module for code generation, with the subtarget's feature string parsed for the first function,
  was 40% of the instructions of a tiny compile.
- `nautilus-nir-run` runs the corpus on `mlir` too (`nir-run-mlir-*`): a natively unwinding executable is called through a
  typed function pointer (dyncall's kernel has no unwind information). Mutation check: breaking the minimum-divided-by-minus-one
  check, the shift mask or the saturating cast fails exactly `division`, `shifts` and `casts`.
- The LLVM IR tests (`ENABLE_LLVM_IR_TEST=ON`, `llvm-ir-test` job) run on the NIR pipeline; their reference IR was
  regenerated from it. `debug`, `perf` and `perf.sample` still select the 0.3 pipeline (and so `MLIRLoweringProvider` with
  the `IRLocationMap` source), see the plan's M4.5 notes.

## `asmjit` on NIR (0.4, M4.4)

- `asmjit/X64NirLowering.cpp` and `asmjit/A64NirLowering.cpp` lower SSA NIR to AsmJit's `Compiler`; `AsmJitNirBackend` is
  the registered NIR backend, `AsmJitCompilationBackend` hands it a graph that carries a module and no IR. AsmJit's
  register allocator and the post-RA peepholes are the 0.3 ones. The 0.3 providers (`X64LoweringProvider`,
  `A64LoweringProvider`) stay for `tracing.nirTracer=false` (`legacy-asmjit`) until M4.2 deletes them.
- Side tables are arrays indexed by the value id of the function (`Fn` in the lowering: registers, use counts, block of
  a value, deferred constants and address parts). A virtual register is created when a value is first needed; only a
  value that is defined and dead within one block, with a single use, hands its register to the instruction that uses
  it (`canReuse`). Constants and traced addresses (`ptr.const`, `data.addr`, `bind.addr`) emit nothing: each consumer
  takes an immediate or rematerialises.
- Integers are not kept extended. x86-64 runs narrow operations on 32-bit registers, AArch64 on W registers; consumers
  that read more extend (division, right shifts, widening casts, compares of 8 and 16 bits on AArch64, calls and
  returns by the extension kind of the signature, 13 §4.5.1). A `bool` is kept as 0 or 1 (AArch64 re-normalises
  parameters and call results, since `cbnz` reads the whole W register).
- D10/D11: checked `div`/`rem` compare and branch to a cold block after the body that calls `nautilus_rt_throw_arith`
  through its capture thunk and jumps to the pad or the exit; narrow shift amounts are masked (32- and 64-bit shifts are
  masked by the hardware); float to integer casts are `cvtt` plus a cold fixup on x86-64 (NaN 0, overflow the extremes),
  `fcvtzs`/`fcvtzu` (which saturate) plus a clamp for narrow results on AArch64.
- Instruction selection kept from 0.3, with the same options and `asmjit.lowering.*` counters: compare and branch
  fusion, loop rotation, address fusion, cmov/csel, immediates, small-callee inlining; AArch64 also tail duplication
  (a block that is lowered twice defines its values into the same registers and reuses none).
- Intrinsics: the plugins' handlers get an `IntrinsicCallContext` (argument registers, result register) and serve the
  0.3 and the NIR lowering alike; the handler is found by the `IntrinsicRegistry` id of the intrinsic's fallback.
- Test the lowering with `nir-run-asmjit-*` (the `.nir` corpus), the execution tests, and `AsmJitLoweringModeTest` /
  `PostRAPeepholeTest`, which pin the counters and the differential behaviour of each option.
- Cost: the statistics split the backend into `asmjit.lowering.ms` (the builder nodes, this file) and
  `asmjit.finalize.ms` (AsmJit's register allocation, the peephole pass and the encoding), which is most of it. AsmJit's
  work grows with the virtual registers and nodes it is given, so a result takes the register of an operand that dies
  (`destGp`, `canReuse`) and a doubled value plus a constant is one `lea`. Check a change with callgrind on
  `nautilus-latency-corpus 1 straight 1000 asmjit` (`lowerNirModule` inclusive) and with `tools/asm-diff/loop-diff.py`.
- Run time: integer arithmetic runs on the whole 64-bit register on x86-64 whatever the type's width (immediates are
  those of the width): a 32-bit `add` of a loop counter measured 30-50% slower than the 64-bit one in the `sum` kernel.
- Measure compile time with `nautilus-compile-bench <reps> all asmjit` (the NIR rows run on `asmjit` natively; the
  `lower_ms` and `final_ms` columns split the backend). On the dev machine of M4.4 (Release, clang-21, one pinned core)
  `straight` 5000 costs 0.07 us per NIR instruction in the lowering and 0.28 in AsmJit's finalize (about 80% of the
  backend); the lowering's own work is under 10% of the instructions executed, so what is left is AsmJit's allocator.
- Code-quality gaps against the 0.3 lowering (x86-64, `loop-diff.py` instruction counts of the loop bodies, run time
  ratio NIR/0.3 in brackets): load plus widening cast is one `movsx`/`movzx` from memory, narrow8/16 13 -> 8 [0.56];
  blocks that only branch are threaded and the post-RA peephole skips unreferenced labels, stride3 21 -> 16 [0.97],
  countNonZero 9+6 -> 8 [0.65]; `a+b`/`a+c` is a `lea` only when `a` is used later in the block (otherwise the
  register allocator coalesces the two-address form, which a `lea` would not); chains of constant adds fold into one
  (`lowerAddChain`: manyArgsLoop 11 -> 9, 0.3 has 10). Open and not worth it so far: the `mov` of a loop-carried value on
  the back edge (the allocator's choice), `setcc` partial writes and select by flags, demanded-bits removal of
  extensions. Passing constant call arguments as invoke immediates only moved the move into the allocator.
- Callgrind of `loopBody` 1000 (backend, `lowerNirModule` inclusive) went 7.71M -> 6.16M instructions without changing a
  byte of generated code: no `snprintf` name per virtual register (584 instructions each; `[Nautilus]` in
  `core/compiler.cpp`), a memo of `queryRWInfo` per instruction shape in `x86::RACFGBuilder` (`[Nautilus]`), a peephole
  that walks the list of jumps instead of all nodes, one use-count pass and one `scaledOf` per side in the lowering.
  Check such a change with the assembly dump of `nautilus-asm-kernels dump` before and after (it must be identical).
- Floor: AsmJit's finalize is about 0.3 us per NIR instruction on linear code (backend total about 0.37 against the
  0.25 target); a `[Nautilus]` fast path in `queryRWInfo` would be worth at most 11-15% of it.
- Not mirrored in `A64NirLowering.cpp` (no way to run AArch64 code in the sessions that wrote this): load plus
  extension fusion, block threading, the `lea` rule, constant add chains, reassociation and constant block parameters.

## Imported calls (0.4, M4.6)

- A call of an `imported` callee goes through the import slot of its module (`HostEnvironment::imports`, the
  `link::ImportSlots` of the graph's link; `module.callees[c].target` is the slot index): load the cell, call the
  entry point with the C convention of the signature. `tbc` uses `LOAD` + `CALL_IND` (the loaded address orders the
  call), `asmjit` a `mov` + `mov [slot]` (x86-64) or `ldar` (AArch64) + `invoke`, `cpp` `__atomic_load_n(..., ACQUIRE)`,
  `mlir` `llvm.load atomic acquire` + an indirect call with the extension attributes of the narrow arguments.
- The exporter's tier decides whether it throws natively or captures, and promotion changes it, so the backends do not
  assume it: a call with an unwind entry other than `NO_UNWIND` goes through the import's thunk, `captureThunk` for
  `tbc`/`asmjit` (an external call with the loaded entry point as the thunk's first argument), `frameThunk` for `mlir`.
  `cpp` catches natively in the generated code. A call that cannot throw (`NO_UNWIND`) is a plain indirect call.
  `functionsNeedingCapture` already counts such a call as an exceptional call site. Without a thunk (a module that did
  not come from the C++ front end) the call is direct and the modes must match.
- `funcaddr` of an imported callee throws `NotImplementedException` on every backend (the stub through the slot is not
  built; nothing takes such an address).

## Fixed cost per compile

What a compile costs before the size of the function counts, measured with `nautilus-fixed-cost-bench [reps [kernel
[backend]]]` (`-DENABLE_BENCHMARKS=ON`; one engine, the same tiny kernel registered many times, the wall time of
`registerFunction` against every duration statistic, `FIXED_COST_CALL=1` adds the first call) and with callgrind on it
(`valgrind --tool=callgrind ... nautilus-fixed-cost-bench 200 add asmjit`; `NautilusModule::compile()` inclusive).

- Nothing per compile may depend on the number of options or on the environment: option names are looked up as
  `string_view` (`EngineOptions::getOptionOrDefault`), and a compile without a `dump.*` option never builds a dump path
  or asks whether a dump is enabled (`EngineOptions::hasDumpOptions`, `DumpHandler`).
- Statistics are cheap to record and free to keep: no allocation per entry, and the counters that a stage holds as a
  struct (`tracing.*`, `conversion.*`) are registered with `CompilationStatistics::defer` and become entries when someone
  reads the statistics. A writer asks `containsDirect`, not `contains`, which would expand them.
- A backend does not pay for what only some programs use: tbc builds the native closure of a function (an `mmap`, an
  `mprotect` and an `munmap`) when its address is first taken (`closureEntry`).
- mlir: code generation goes through the target machine of the thread (see State reuse); the rest of a tiny compile is
  LLVM's: building the codegen pass pipeline (~2.3 of ~7.8 million instructions), the optimizer, the MLIR conversion passes.
- cpp: the compile is the system compiler. `posix_spawnp` replaces `popen`'s `sh`, `-pipe` overlaps `cc1plus`, `as` and
  the linker, and the generated source defines `int8_t`..`uintptr_t` itself (`CPPPreamble.hpp`) instead of including
  `<cstdint>`. What is left, measured for gcc 13: `cc1plus` starting up on an empty file 7-9 ms, `as` 3, the link through
  the driver 11 (`ld` alone 4; the driver, `collect2` and the LTO plugin are the rest), none of which a flag removes.
  `-g` costs nothing measurable on small sources; `clang++` as the compiler is 3-6 times slower.
