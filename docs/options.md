# Nautilus Runtime Options

Nautilus provides various runtime options to customize the compilation. Options come in two scopes:

- **Engine** – passed when initializing the Nautilus engine (`NautilusEngine(options)`). They configure the
  engine-owned, built-once compiler and therefore apply to every module compiled by that engine. Engine-only options
  cannot be overridden per module.
- **Module** – every option below can be set on the engine to provide an engine-wide default. The options marked
  *Module* in the **Scope** column can additionally be **overridden for an individual compiled module**, either by
  passing a `ModuleOptions` to `engine.createModule(overrides)` or by calling `module.setOption(name, value)` before
  `module.compile()`. A module inherits all engine-wide values and overrides only what it sets.

See [engine.md](engine.md) for how to create modules and override options per module.

| Option                                      | Default | Scope | Type | Code | Description |
|---------------------------------------------|----------|---------|------|------|------------------------------------------------------------------------------------------------------------------------------------------------------|
| engine.compilation=[true,false]             | true     | Engine  | bool | no | Activates the compilation of nautilus functions. If the flag is false, all nautilus functions will be directly invoked, which is handy for debugging. |
| engine.backend=[mlir,cpp,tbc,asmjit,nirtbc] | -        | Engine  | enum | no | Pins a single compilation backend: the engine compiles single-tier, synchronously, with exactly this backend (no tier-0 compile, no background promotion). `nirtbc` is a pseudo-backend for the tests (see `tracing.nirChain`). When unset, the engine runs the default tiered compilation. |
| engine.tier0.backend / engine.tier1.backend | see desc. | Engine  | string | no | Configures the fast (tier 0) and optimized (tier 1) backends for tiered compilation. Each can be set alone; the other keeps its default. Ignored when `engine.backend` is set. By default tier 1 is `mlir` (the default backend of the build if `mlir` is not built) and tier 0 is selected by availability in the order `asmjit`, `tbc`, `interpreter`. Tier 0 also accepts the special value `interpreter`: the module runs uncompiled (direct invocation) until the background tier-1 compilation completes. A backend that is unknown or not built fails at engine construction. |
| engine.tiered.backgroundPromotion=[true,false] | true  | Engine  | bool | no | **Deprecated alias** of `engine.tiered.promotion` (`false` maps to the internal value `none`, `true` to the default). When true, the engine compiles with the tier-0 backend immediately and promotes to the tier-1 backend in the background. When false, it compiles single-tier with the tier-1 backend (synchronous, no promotion). |
| engine.tiered.promotion=[eager,manual] | eager | Engine | enum | no | When a module is promoted to tier 1: `eager` queues the promotion right after conversion, before the tier-0 code generation; `manual` only on `CompiledModule::promote()` (the embedder decides, for example once a query is known to be long-running). Setting `none` directly is rejected; the value exists only as the target of the deprecated `engine.tiered.backgroundPromotion=false`. See [engine.md](engine.md#tiered-compilation-and-promotion). |
| engine.tiered.promotionThreads | max(1, cores / 4) | Engine | int | no | Number of worker threads of the engine's promotion service, which runs the tier-1 compiles of all modules of the engine. The workers are created with the first promotion, run at a lower OS priority and live as long as the engine, so the thread count does not grow with the number of modules. Must be at least 1. |
| engine.tiered.maxQueuedPromotions | unbounded | Engine | int | no | Number of promotions that may wait for a worker. A promotion beyond it is not queued: its module stays on tier 0 with the status `skipped`. `0` skips every promotion. Promotions of modules that were dropped do not count. |
| engine.normalizeFunctionNames=[true,false]  | false    | Module  | bool | no | Generates normalized function names (runtimeFunc0, runtimeFunc1, etc.) during tracing instead of using actual function names. Useful for deterministic output and testing. |
| engine.foldStaticConstants=[true,false]     | true     | Module  | bool | yes | Folds, while tracing, operations over values C++ already knows: the byte offset of `ptr + n`, `ptr[n]`, `ptr.get(&S::field)`, `++`/`--` for a raw integer or `static_val` `n` is traced as one constant (`ptr + 0` as a copy), a traced offset into a byte pointer is not multiplied by 1, and a literal or a `static_val` in `val OP literal` is traced as a constant of the type the operator converts it to instead of a constant plus a `CAST` (when that conversion is exact for every value of the literal's type). No traced value is consulted, so this is sound in loops and across branches. Set it to `false` to trace these operations unfolded, e.g. to compare traces. See [pointers.md](pointers.md#what-pointer-arithmetic-traces). |
| engine.demangleFunctionNames=[true,false]   | true     | Module  | bool | no | Demangles C++ function names to human-readable format when they are resolved (see `resolveFunctionNames`). When disabled, uses mangled names as-is. Ignored if normalizeFunctionNames is enabled. |
| engine.resolveFunctionNames=[true,false]    | false (true if `debug`/`perf`) | Module  | bool | no | Resolves the symbol names of `invoke()`d native functions and destructors (`dladdr` + demangling, after tracing and cached process-wide) so the IR, dumps and generated code name them. `dladdr` scans the symbol table of the containing object and can cost about 1 ms per callee in large binaries, and names never change the generated code's behaviour -- callees are identified by address -- so by default they are resolved only when the compiled code will be inspected, i.e. when `debug`, `perf` or `perf.sample` is set; otherwise such callees are named `fnN`. Setting this option explicitly overrides that default. `normalizeFunctionNames` does not depend on it. |
| engine.logStatistics=[true,false]           | false    | Module  | bool | no | Logs compilation statistics (timings, entity counts) after compilation.                                                                              |
| engine.arena.retainedBytes                  | 8388608  | Engine  | int  | no | Upper bound in bytes on the idle memory the engine keeps for its trace and IR arenas (in the shared chunk pool and the per-thread caches). Chunks beyond it go back to the OS immediately; idle chunks lose their pages after 200 ms and are unmapped after 5 s. `NautilusEngine::trimMemory()` gives all of it back at once. |
| dump.all=[true,false]                       | false    | Module  | bool | no | Dumbs intermediate representations all compilation steps.                                                                                             |
| dump.copySites=[true,false]                 | false    | Module  | bool | no | Dumps `copy_sites.txt`: every copy recorded while tracing (an `ASSIGN` to a fresh value, made by a `val` copy constructor), grouped by the C++ call chain that made it, from the copy up to the first frame outside nautilus, and by that frame alone. Use it to find the copies that dominate tracing time and remove them where they are made (`const&` parameters, moves). Frames resolve to `function (file:line)` when the binaries have debug information and `ENABLE_STACKTRACE` is on. Not included in `dump.all`: resolving the stacks is slow. The copies are recorded by the 0.3 tracer only, so setting this option compiles with the 0.3 pipeline (as `tracing.nirTracer=false`). |
| dump.after_tracing=[true,false]             | false    | Module  | bool | no | Dumbs traces directly after trace generation.                                                                                                         |
| dump.after_nir_tracing=[true,false]         | false    | Module  | bool | no | Dumps the trace as pre-SSA NIR text (`nautilus-nir-opt` reads it), next to the 0.3 trace of `dump.after_tracing`. |
| dump.after_nir_conversion=[true,false]      | false    | Module  | bool | no | Dumps the SSA NIR the conversion made from the trace (NIR pipeline), as text. |
| dump.after_nir_passes=[true,false]          | false    | Module  | bool | no | Dumps the SSA NIR a backend is given after the optional passes and the plugin passes changed it (NIR pipeline), as text. Not written for a compile in which no pass changed the module. |
| tracing.verifyNir=[true,false]              | false    | Module  | bool | no | Runs the NIR verifier on the pre-SSA module of every trace and on the SSA module the conversion made from it (the 0.3 pipeline maps its trace to pre-SSA NIR for this); a violation fails the compilation with the diagnostics. `ir.verifyAfterEachPass` (the `NAUTILUS_IR_VERIFY=1` hook of the tests) turns it on too. Used by the tests to check the NIR tracer and the conversion against every traced function (`NAUTILUS_OPTIONS="tracing.verifyNir=true"`). |
| tracing.nirAttributesFile                   | -        | Module  | string | no | Converts every trace to NIR and appends one line per internal function (name, tab, the derived guarantee bits of the attribute pre-pass) to this file. The execution tests compare it with the recorded 0.3 attributes (`nautilus/test/baselines/0.3`). |
| tracing.nirChain=[true,false]               | false    | Module  | bool | no | With the 0.3 tracer (`tracing.nirTracer=false`): maps every trace to NIR, converts it to SSA and attaches it to the IR graph for the `nirtbc` pseudo-backend, which compiles the NIR with the `tbc` backend on NIR instead of the IR. The execution tests run it as `nir-tbc` to check the mapping from the 0.3 trace. Has no effect with the default pipeline. |
| tracing.unwindPausedPasses=[true,false]     | false    | Module  | bool | no | NIR tracer: when a pass of a traced body reaches an operation that was already recorded (a control-flow merge), the pass is over, but the body would run to its end on the paused path. With this option the tracer leaves the body at that point with a private exception that its scope catches, so a re-run costs one throw instead of the rest of the body (`tracing.pausedOperations` drops to about 0, `tracing.unwoundPasses` counts the throws). User code that swallows it with `catch (...)` is detected (`tracing.unwindFallbacks`): that scope runs its passes out as before. A `noexcept` frame or a destructor between the tracer and the scope would terminate the process, which is why the option is not the default; see [tracing.md](tracing.md). |
| tracing.forceConstructRestarts=[true,false] | false    | Module  | bool | no | NIR tracer, for tests and the fuzzer: every arm, loop header, body and step of an explicit construct (`If`, `While`, `For`, `nautilus/control_flow.hpp`) starts over once after its first pass, as it does when it meets a native branch, so that the rollback of what an optimistic scope recorded is exercised by every construct (`tracing.constructRestarts` counts the restarts). The traces and the compiled code do not change; the tracing time does. See [control-flow.md](control-flow.md#explicit-control-flow). |
| engine.diagnostics=[off,text,json]          | off      | Module  | enum | no | Writes the tracing diagnostics (`NAUT-T001` and the others of [diagnostics.md](diagnostics.md)) to standard error as they are raised: `text` as one line with the code, the source location, the message and the hint, `json` as one JSON object per line for tools. The diagnostics are in the compilation statistics (`diagnostics.count`, `diagnostics.<n>.code`) and an error fails the compilation with its text in every mode. |
| tracing.diagnostics.maxPasses               | 256      | Module  | int  | no | The number of passes of one scope from which `NAUT-T002` (path explosion) is raised. |
| tracing.diagnostics.replayedOperations      | 100000   | Module  | int  | no | The number of replayed operations from which `NAUT-T003` (replay share) is raised, if re-runs also took more than half of the pass time. |
| tracing.nirTracer=[true,false]              | true     | Module  | bool | no | Selects the compilation pipeline. `true` (the default) is the NIR pipeline: the direct NIR recorder (`FlatTrace`) traces, the conversion makes SSA NIR from it, and the backend compiles that: `tbc`, `cpp` and `asmjit` take NIR as it is, `mlir` gets the 0.3 IR built from it by a temporary bridge (the D10/D11 semantics of NIR are not applied by it yet). `false` (or `dump.copySites`, which needs the tags of the 0.3 trace) is the 0.3 pipeline (`TraceContext`, `ExecutionTrace`, the IR passes of the `ir.*` options), kept as a fallback for one release; the `ir.*` options other than `ir.runPasses` and `ir.runOptimizationPasses` configure it only. |
| dump.after_ir_creation=[true,false]         | false    | Module  | bool | no | Dumps the nautilus ir after generation: the 0.3 trace converted to IR, or with the NIR pipeline the IR the bridge built from NIR for a backend that takes it (`mlir`). |
| dump.after_mlir_generation=[true,false]     | false    | Module  | bool | no | Dumbs the generated mlir if the MLIR backend is used. `region()` annotations on the emitted ops come from the IR location map, so they are present only when `debug` or `perf` is also set. |
| dump.after_llvm_generation=[true,false]     | false    | Module  | bool | no | Dumbs the generated llvm if the MLIR backend is used.                                                                                                 |
| dump.after_cpp_generation=[true,false]      | false    | Module  | bool | no | Dumbs the generated cpp code if the CPP backend is used.                                                                                              |
| dump.after_tbc_generation=[true,false]      | false    | Module  | bool | no | Dumps the generated threaded bytecode if the tbc backend is used. |
| dump.after_asmjit_generation=[true,false]   | false    | Module  | bool | no | Dumps the instruction stream the AsmJit backend generated, before assembling. |
| dump.after_asmjit_assembly=[true,false]     | false    | Module  | bool | no | Dumps the machine code the AsmJit backend assembled, as a disassembly. |
| dump.console=[true,false]                   | false    | Module  | bool | no | Enables the dumping of intermediate compilation steps to the console.                                                                                 |
| dump.file=[true,false]                      | true     | Module  | bool | no | Enables the dumping of intermediate compilation steps to a temp folder.                                                                               |
| dump.graph=[true,false]                     | false    | Module  | bool | no | Dumps a graph representation in either (mermaid or graphvit) to a file.                                                                               |
| dump.graph.type=[mermaid,graphviz]          | graphviz | Module  | enum | no | Sets the type of the graph.                                                                                                                           |
| dump.graph.full=[true,false]                | false    | Module  | bool | no | Represents both data and control-flow (full=true) or only the control-flow (full=false).                                                              |
| ir.runPasses=[true,false]                   | true     | Module  | bool | yes | Runs the IR passes at all. Off, none of the optional passes of the NIR pipeline (`ir.inline`, `ir.enableLICM`, `ir.enableStrengthReduction`, the optional passes of plugins) runs. The required passes of plugins run regardless, since they are part of what the module means. For the 0.3 IR that backends without a NIR port get, it also switches off the exception-handling analyses their landing pads come from. |
| ir.runOptimizationPasses=[true,false]       | see desc. | Module | bool | yes | Pins whether the optional passes run. `true`: they run in every compile of the module, the tier-0 compile of a two-tier module included. `false`: none runs. Unset, they run in every compile but the tier-0 compile of a module that is promoted (a latency-critical compile): tier 0 gets the code of the conversion, tier 1 the optimized module. Which optional passes there are is decided by their own options, all off by default; with none enabled a compile pays for nothing (`irPasses.pipelineIterations` is 0). For the 0.3 pipeline (`tracing.nirTracer=false`) it keeps its 0.3 meaning, pinning the whole IR optimization pipeline.
| ir.disableDeadCodeElimination=[true,false]  | false    | Module  | bool | yes | **No longer has a pass in the NIR pipeline**: the conversion removes dead values and block arguments itself. Accepted and ignored there, with a deprecation warning; the 0.3 pipeline (`tracing.nirTracer=false`) still honors it. Disables the pass that removes pure, unused operations. |
| ir.disableAlgebraicSimplification=[true,false] | false | Module  | bool | yes | **No longer has a pass in the NIR pipeline** (the conversion applies the rules while it emits). Accepted and ignored there, with a deprecation warning; the 0.3 pipeline still honors it. Disables local algebraic simplifications. |
| ir.disableConstantBranchFolding=[true,false] | false   | Module  | bool | yes | **No longer has a pass in the NIR pipeline** (a branch on a constant adds only its taken edge). Accepted and ignored there, with a deprecation warning; the 0.3 pipeline still honors it. Disables folding branches on constants. |
| ir.disableBlockMerging=[true,false]         | false    | Module  | bool | yes | **No longer has a pass in the NIR pipeline** (the conversion threads single-predecessor blocks). Accepted and ignored there, with a deprecation warning; the 0.3 pipeline still honors it. Disables merging blocks into their sole predecessor. |
| ir.disableBlockArgumentPruning=[true,false] | false    | Module  | bool | yes | **No longer has a pass in the NIR pipeline** (trivial block arguments are folded and the dead-value sweep removes the rest). Accepted and ignored there, with a deprecation warning; the 0.3 pipeline still honors it. Disables removing unused or redundant block arguments. |
| ir.enableLocalCSE=[true,false]              | false    | Module  | bool | yes | **No longer a pass in the NIR pipeline**: the conversion always does block-local CSE. Accepted and ignored there, with a deprecation warning; the 0.3 pipeline still honors it. |
| ir.enableLICM=[true,false]                  | false    | Module  | bool | yes | Enables the loop-invariant code motion pass of the NIR pipeline (an optional copy pass, [03 §5](plans/nautilus-0.4/03-conversion-and-passes.md)): instructions with no effect that cannot throw and read no memory move into the preheader of their loop, which the pass makes where the loop is entered through a branch. Loads, stores, checked divisions and calls with effects stay. Runs where the optional passes run (see `ir.runOptimizationPasses`). |
| ir.enableStrengthReduction=[true,false]     | false    | Module  | bool | yes | Enables the strength-reduction pass: `base + i * stride` in a loop whose 64-bit index `i` the one back edge advances by a constant, with a constant stride and a loop-invariant `base`, becomes a pointer the back edge advances by `step * stride`. Runs where the optional passes run. |
| ir.inline=[true,false]                      | false    | Module  | bool | yes | Enables the inlining pass: a call of an internal callee is replaced by the callee's body (callees first, so a chain of small functions collapses), when the callee is not recursive, has at most `ir.inline.maxInsts` instructions and no function string attributes; the internal functions nothing refers to afterwards are removed. With `ir.inline.crossModule` the body of an imported callee is copied from its exporter. Runs where the optional passes run. |
| ir.inline.maxInsts=[int]                    | 64       | Module  | int | yes | Largest callee, in NIR instructions, that `ir.inline` inlines. |
| ir.inline.crossModule=[true,false]          | true     | Module  | bool | yes | Lets `ir.inline` inline imported callees ([13 §4.4.3](plans/nautilus-0.4/13-nir-spec.md)): the exporter's body is taken from the NIR its module kept when it was compiled. A function that uses `bind.addr`, or reaches one that does, stays an import call. The compiled code records the exporters it inlined (`irPasses.inline.importedModules`). |
| ir.maxPipelineIterations=[int]              | 4        | Module  | int | yes | Rounds of the optional passes: the group of inlining, LICM and strength reduction runs again while one of its passes changed the module, at most this many times. |
| optimizationLevel=[0,1,2,3]                 | 3 (0 if `debug`) | Module | int | yes | Sets the LLVM optimization level for the code-generation if the MLIR backend is used. Overrides the `-O0` clamp `debug` otherwise applies. |
| debug=[true,false]                          | false    | Module  | bool | yes | Top-level gate for DWARF debug-info generation in the MLIR backend, so a debugger can step through and print values in JIT-compiled code. DWARF line-table locations are attached from a Nautilus-IR dump written for this purpose, the LLVM codegen level is clamped (`Less`, and `optimizationLevel` to `0` unless set explicitly) so debug values stay accurate, the MLIR inliner is skipped so frames stay predictable, every `$N` gets a shadow alloca + `dbg.declare`, and the JIT-linked object is registered with the debugger through the GDB JIT interface. A no-op when false. |
| perf=[true,false]                           | false    | Module  | bool | no | Emits perf jitdump records (`JIT_CODE_LOAD` / `JIT_CODE_DEBUG_INFO` / `JIT_CODE_UNWINDING_INFO`) for every JIT-linked object, so `perf record` + `perf inject --jit` can symbolize and attribute samples -- down to `region()` scopes -- inside JIT-compiled code. Linux/ELF only; a no-op with a warning elsewhere. Independent of `debug`: on its own it keeps the requested optimization level and the MLIR inliner running, so the profile reflects *production-optimized* code, the actual point of this option. Setting `debug` and `perf` together still works (`debug`'s `-O0` clamp wins, with a one-time warning that the resulting profile is not representative) -- `optimizationLevel` set explicitly overrides that clamp either way. See `docs/profiling.md` for a full `perf record` / `perf inject` / `perf report` recipe. |
| perf.sample=[true,false]                    | false    | Module  | bool | no | Publishes every compiled code range, with its `region()`-qualified name, into the process-wide `JitSymbolRegistry`, so a sampling profiler running *inside* the process can name JIT frames -- no `perf record`, no `perf inject --jit`, no jitdump file. This is what the `nautilus-profiling` plugin's `profiling::Sampler` resolves against; see `docs/perf.md`. Independent of `perf`: the two write the same names for an in-process and an out-of-process reader respectively, and either, both or neither may be set. Like `perf` it clamps nothing, so the profile reflects production-optimized code. `mlir` and `asmjit` (and the copy-and-patch mode of `tbc`, `tbc.mode=jit`) publish their code, so the default tiers work too; the interpreting mode of `tbc` has no generated code to publish, and its handlers are named by the host's own symbols. `asmjit` and `tbc` write the text form of the module (NIR) to a file in the working directory and publish the line table into it, so `JitSymbolRegistry::resolveLine` attributes an address to a NIR instruction. Linux only. |
| mlir.enableMultithreading=[true,false]      | false    | Module  | bool | no | Gives the MLIR context a thread pool of its own. Off by default since the NIR port: a compile lowers one module, and the context is kept by the compiling thread between compiles (see `MLIRThreadState`), so a pool per worker would only cost threads. |
| mlir.enableIntrinsics=[true,false]          | true     | Module  | bool | yes | Registers the MLIR intrinsic plugins for this compilation.                                                                                            |
| mlir.inline_invoke_calls=[true,false]       | false    | Module  | bool | yes | Allow MLIR Backend to inline functions that were tagged with NAUTILUS_INLINE                                                                          |
| mlir.eager_compilation=[true,false]         | false    | Module  | bool | no | Generates machine code during compilation, so the compile statistics include it and the first call does not pay for it. When disabled, LLVM generates it on the first call of a compiled function. |

## Environment Variables

| Variable                   | Description                                                                                                                                                                                          |
|----------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| NAUTILUS_STATISTICS_FILE   | Path of a file that every compilation appends its statistics to, as one JSON object per line (the entries `engine.logStatistics` reports). Measures an application's compilations without changing its options. |
| NAUTILUS_OPTIONS           | Options layered over every engine's own, as `key=value` pairs separated by `;` (e.g. `engine.backend=asmjit;mlir.eager_compilation=true`). `true`/`false` set booleans, numbers set integers or doubles, anything else a string. Reconfigures an application's compilations without changing its code. |
| NAUTILUS_DETERMINISTIC     | `1` makes two runs of the same binary execute the same instructions: compilation unit ids come from a counter instead of the clock and the entropy source, and the process token of NIR modules is a constant. For measurement only (the callgrind gate, `tools/latency`): the unit ids of two processes then collide, and the process token no longer tells processes apart. |
