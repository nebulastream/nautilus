LLVM pass ablation

Each row removes every instance of one pass from the expanded default pipeline and compares the result with the unmodified expanded pipeline. A negative compile change means the pass costs that much compile time. A positive runtime change means the code is that much slower without the pass. Own time is the pass's exclusive time in the profile of the same level, as a share of the compile metric; indirect is the saving minus that own time, both as shares of the total over the selected kernels: work later passes and code generation do because of what the pass produced. Small values (a few percent) are within measurement noise. Passes in the top-left of the trade-off are cheap to keep and costly to lose.

Why passes are slow

Pass profiles of the default O0–O3 pipelines, O3 without the LLVM inliner, and the greedy pipeline, recorded with mlir.recordPassTimings. Every time is exclusive: a pass does not own the analyses it requests or the passes nested in it. Means per compilation over the selected kernels. A pass whose own time is small can still be expensive overall: compare its own time here with what removing it saves in the ablation above. The difference is downstream work it causes, mostly through the IR it produces.
